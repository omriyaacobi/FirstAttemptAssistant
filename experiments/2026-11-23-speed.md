# 2026-11-23: Where does Bot's answer time go, and what cuts it? (to-do t19)

Scripts (all in `experiments/`):
- `speed-measure.js` reads Bot's real thread files and prints only numbers (no message text).
- `speed-lab.js` runs one brain-shaped call with invented context: prompt size × answer length.
- `speed-rounds.js` runs a two-call "tool round" message, with the next agy process started late or early.

Raw lab numbers: `speed-lab-results.json`, `speed-rounds-results.json`. All model calls were Neon low or Neon medium (the
"Gemini Models" pool): about 50 calls in total. No Claude plan was used, and nothing went through the running Bot.

## Short answer (simple words)

- **A typical answer takes 11-14 s; one with a lookup takes about 22 s.** Real numbers, 212 answers from 20-23 Nov: median
  13.9 s, slowest 10% over 27.7 s. Almost all of it (12.6 of 13.9 s) is the model call itself. Bot's own code (building the
  prompt, the calendar, running tools) takes about 0.9 s. Waiting in the queue is about 0.05 s.
- **The model's time is about 4 s fixed plus the time to WRITE the answer.** The fixed part is agy starting up, the network,
  and the time to the first word. The writing goes at about 150-200 tokens a second, counting the hidden "thinking" tokens
  too. Real answers write about 570 tokens and think about 390, so that is about 5 s on top of the 4.
- **The prompt's size hardly matters for speed.** Doubling it from 10k to 20k input tokens cost about 0.2 s (4.5 s vs 4.7 s).
  A short prompt is still worth having, but for the quota, not for the speed.
- **agy takes 3.4 s just to start.** Bot hides this by keeping a "spare" agy process waiting, but three cases still paid it.
  All three are fixed on this branch:
  1. **The second call of a message that used a tool.** The spare for it was started only after the first call ENDED, so the
     second call waited for it. Starting it when the first call starts: **8.0 s -> 4.8 s** for that call (12 messages; the
     first call was not slower, 4.9 vs 5.0 s). That is 49 of the 212 messages, with about 3.2 s saved per extra round.
  2. **Neon medium, the model Omri picked with the picker on 22-23 Nov (62 calls), never had a spare.** It was missing from
     `WARM_MODELS`, the same bug t16 fixed for Neon low. Measured warm vs cold: **5.0 s vs 8.1 s**. Argon medium and Sonnet in
     agy were missing too.
  3. **A message after more than 8 minutes of quiet** (21% of messages). The spare is thrown away after 8 idle minutes, so
     the next message started agy cold. Now the page tells Bot "Omri is typing" (never the words). Bot then starts the spare of
     the model most likely to answer, and reads the calendar, while Omri types. This saves up to 3.4 s on those messages. In
     the real log those messages were only 1.2 s slower in the middle, because answer length varies a lot.
- **The calendar read (about 0.4 s on most messages) now runs at the same time as the course pages are picked**, instead of
  before them. The typing ping usually has it read before the message arrives.

## 1. What is real now (`node experiments/speed-measure.js <data> 2026-11-20`)

"total" is Bot's own clock from taking the message to the answer being ready. "model" is the sum of the model calls' seconds.
"other" is total minus model: building the prompt, running tools, and waiting for a slot.

| group | n | median total s | slowest 10% s | median model s | median other s | median tokens |
|---|---|---|---|---|---|---|
| all | 212 | 13.9 | 27.7 | 12.6 | 0.9 | 25,835 |
| Neon low answered | 111 | 11.2 | 20.9 | 10.0 | 0.9 | 24,929 |
| Neon medium (Omri's pick) | 50 | 17.8 | 30.5 | 16.8 | 0.9 | 27,008 |
| Argon low | 42 | 19.8 | 34.0 | 18.8 | 0.7 | 45,571 |
| 1 model call (direct answer, or a doing-tool and done) | 160 | 11.7 | 21.0 | 10.8 | 0.9 | 25,079 |
| 2 model calls (one lookup round) | 42 | 22.1 | 32.7 | 19.9 | 1.0 | 51,363 |
| 3 model calls | 7 | 32.4 | 57.7 | 29.3 | 6.3 | 67,334 |
| agy's own web search inside the call | 17 | 23.1 | 34.1 | 22.3 | 0.8 | 48,964 |

One model call, per model ("1st" is the first call of a message; "later" is the call after a tool round):

| model | 1st call median s (n) | later call median s (n) |
|---|---|---|
| Neon low | 8.7 (106) | 10.8 (27) |
| Neon medium | 13.2 (50) | 16.8 (12) |
| Argon low | 11.8 (38) | 10.2 (13) |

Too few calls to judge for Hydrogen medium (2) and Sonnet in agy (1).

- **Tokens per call** (`data/token-log.json`, 20-23 Nov): about 20-25k input tokens per call (not 9k as first thought; the
  briefing alone is 27,700 characters, about 7k tokens), about 570 output and about 390 thinking for Neon low. Neon low never
  reported a cache hit (cacheRead 0), so nothing is reused from one call to the next.
- **The 0.9 s of "other"** on a direct answer is about 0.4 s for the Google Calendar read (it was cached for only 1 minute,
  so most messages read it again) and about 0.5 s for the course part. Most of that is picking the notes: 50-190 ms per
  course over 114-494 pages, measured read-only on the real data.
- **Tool rounds:** 49 of 212 messages needed another model round after a tool. They are 36% of all waiting time. The first
  tool in those was usually a real lookup (project_read 18, course_read 12, course_files 4, lecture_parts 3). Those rounds
  are needed: the model must read the file before it can answer.
- **Queueing:** the time from the message arriving to the brain starting is about 0.05 s (worst 5%: 0.1 s). Queueing is not a
  problem.

## 2. Experiments

### a) Prompt size vs answer length (`speed-lab.js`, Neon low, warm spare, 5 runs each)

| arm | median s | median first words s | input tokens | output | thinking |
|---|---|---|---|---|---|
| small prompt, one-line answer | 4.5 | 4.3 | 9,641 | 167 | 118 |
| big prompt, one-line answer | 4.7 | 4.3 | 19,989 | 143 | 103 |
| small prompt, a few paragraphs | 13.2 | 8.6 | 9,658 | 1,281 | 696 |
| big prompt, a few paragraphs | 10.3 | 5.0 | 20,007 | 815 | 189 |

The time follows output + thinking, not input. The "few paragraphs" arms differ only because the model happened to write and
think less in the big-prompt runs. The first words reach the page only after the thinking is done; from then on the page
shows the answer as it is written. So for a long answer, the time to the first words (5-9 s) is what Omri feels.

Neon low is already the lowest thinking level agy offers (`agy models` lists low, medium, high and xhigh), so there is no
cheaper level to try.

### b) The second call of a tool message (`speed-rounds.js`, Neon low, 6 messages per arm, arms alternating)

| arm | call A s | call B s | both s | worst both s |
|---|---|---|---|---|
| after (Bot until now) | 4.9 | 8.0 | 13.1 | 15.6 |
| early (this branch) | 5.0 | 4.8 | 10.0 | 13.2 |

With "after", the spare was never ready when call B came (0 of 6). With "early" it was ready 6 of 6 times.

### c) agy's start-up, and warm vs cold for Neon medium

- From starting agy to its "init" event: 3.2-3.9 s, 6 times, median 3.45 s.
- Neon medium, the same short question: warm 5.0, 4.1, 5.0 s; cold 8.1, 12.6, 7.9 s.

## 3. What was changed (this branch)

- `warmagy.js`: a new option `early`. The spare for the next call is started when a call starts, not when it ends. It is
  off by default and the brain turns it on. Still one process per call, so nothing is shared between messages.
- `brain.js`:
  - `WARM_MODELS` now holds every agy model the chain or the picker can put first: Neon low and medium, Hydrogen medium,
    Argon low and medium, and Sonnet in agy.
  - `warmUp()` starts the spare of Omri's picked model, or else the one that answered last, or else the chain's first. It
    also reads the calendar. Only one Google read runs at a time (`refreshCalendar`).
  - The calendar read now starts before the rest of the prompt is built, and is awaited at the end.
- `server.js`: `POST /api/brain/warm` (JSON only, same login as every route, at most once every 20 s, empty body).
- `public/index.html`: typing in the message box sends that ping, at most once a minute. The words are never sent.
- `tests/speed.test.js`: 9 tests, using a fake agy only.
- `tests/brain-quota.test.js`: one test checked the cold agy route using Sonnet in agy as its example. That model is warm now,
  so in the first full run the test reached the REAL warm pool and sent one "hi" to agy's "Claude and GPT models" pool. The
  test now uses agy's Claude medium, which has no spare and is never first in the brain, and it asserts that this model is
  not warm. So it can never call a real model again.

No model is asked by any of this, so it costs no quota. It only starts an agy process a little earlier. It does not bring
back the old every-8-minutes restart (the "game freeze" worry in `brain.js`): a spare is started only when Omri types.

## 4. Recommendations

What is built (above), and the expected effect, from the numbers:

| change | who gains | measured saving |
|---|---|---|
| early spare | messages with a tool round (about 1 in 4) | about 3.2 s per extra round (call B 8.0 -> 4.8 s) |
| full `WARM_MODELS` | every Neon medium / Argon medium / Sonnet-in-agy call | about 3 s per call (Neon medium 8.1 -> 5.0 s) |
| typing warm-up | messages after 8+ quiet minutes (about 1 in 5) | up to 3.4 s (agy's start-up) |
| calendar overlap and early read | most messages | about 0.3-0.4 s |

To check after the merge: `node experiments/speed-measure.js "<data folder>" 2026-11-24`. "later call" should fall about 3 s.
Neon medium's 1st call should drop from about 13 s. "other" should drop below 0.9 s.

Not built, for Omri to decide (each changes something agreed):

1. **Shorter answers are the biggest lever left.** Every 200 tokens of answer is about 1 s. Today's answers average about 570
   output tokens. The briefing could ask for shorter replies by default (the phone line already does). This is a style choice.
2. **The picker's Neon medium costs about 4.5 s per call more than Neon low** (13.2 vs 8.7 s first call). That is the medium
   level's extra thinking, not the spare. Worth knowing when picking it.
3. **Fewer lookup rounds by putting more in the prompt:** a bigger prompt is almost free in seconds (+0.2 s for 10k tokens),
   but costs quota on every call. One example: the whole linked-folder file Omri asks about most. It would save one full call
   (about 10 s) on the messages that read a project file (18 of 212). That trades quota for speed: Omri's call.
4. **Continuing the same agy process for a tool round** (agy's stream-json takes several turns) would stop re-sending the
   20k-token prompt in round 2. That saves tokens but little time (input is cheap in seconds). It also changes the "one
   process, one message" design. Not worth it for speed alone.

## Limits

- One machine, one afternoon. agy's servers vary by a second or more between runs, so differences under 0.5 s are noise.
- The lab prompts are invented (in the shape of Bot's course block), not Omri's real ones. The real-log tables are the
  ground truth for "how fast is Bot today".
- The typing warm-up was tested with a fake agy and a fake brain, not end to end in the browser. Its real effect shows in the
  log after the merge.
