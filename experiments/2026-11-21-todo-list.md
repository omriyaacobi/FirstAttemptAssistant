# 2026-11-21: one shared to-do list for Bot (`data/todo.md`)

**What and why.** The to-do list for building Bot lived in `PROGRESS.md` ("## To do"), which only Claude Code sessions read. When Omri
asked Bot for "the improve bot list (our to-do list)" Bot did not know what he meant. Now ONE file, `data/todo.md` (private,
git-ignored, in the daily encrypted backup), is read and changed by Bot (brain tools) and by every Claude Code session (CLAUDE.md rule).

**The file.** Plain Markdown: `## Section` headings, items `- [ ] [t7] text` (`[x]` done), sub lines indented by two spaces. Code
edits by LINES, so everything else in the file (prose, a hand edit) stays byte for byte. Ids t1-t14 are the old numbers of the
PROGRESS.md list; a new item gets the highest id + 1.

**`todo.js` (checked by code, a model only hands in values).**
- `read({id})`: the whole file, or one item with its sub lines. Read fresh each call (Claude Code may edit in between).
- `update({action, id, text, section})`: `add` (to an existing section; one section name must fit), `done`, `undone`, `reword`, `move`,
  `remove`, `undo`. Checks: action from a closed list, id exists, section name fits exactly one section, text 1-1200 characters, no
  control characters (a tab or newline is turned into a space, so a text can never make a second item or a heading), at most 300
  items and 80,000 characters. Atomic write (temp file + rename). Returns one line of what changed.
- Undo: `data/todo-undo.json` keeps the file as it was before Bot's last change and as Bot left it. `undo` puts it back only within
  2 hours and only if the file is still exactly what Bot left (otherwise someone else edited it and the undo would lose their edit:
  it says so).
- Brain: `todo_read` (a lookup, result inside a data block, capped at 14,000 characters) and `todo_update` (a doing-tool, in `DOING`).
  `todo_update` is refused after a web page, a photo or Moodle text (`afterWeb`, a row in `tests/refusal-rules.test.js` for each),
  and after the message read a course file or a project file (`ctx.sawFile`, set by course_search, course_read, project_read and
  project_grep), so text from a page, a picture or a file never becomes an item. The list is not in every context (tokens): the brief
  tells the model it exists, what Omri calls it ("the to-do list", "the Improve Bot list", "our list") and when to read it. No word
  list or regex on Omri's words.
- Starting a task: the brief tells the model to call the existing `improve_bot` button with the item's text; Omri still taps it and
  approves the change in Improve Bot. Items about guard files, `.env`, installs, logins or real-data research are told to be for Claude Code.

**Real check (Neon low, a FAKE list in a temp folder; `experiments/2026-11-21-todo-real.js`).** Five messages, every one right:
"what's on the to-do list?" -> `todo_read`, a readable list (53 s, a cold first call); "mark the backup item done" -> `todo_update done t1`
(8.9 s); "add to the Later section: ..." -> add (8.6 s); "undo that" -> undo (6.7 s, the fake file was back as before); "start the
24-hour times item" -> `todo_read` + `improve_bot` with the item's text (19 s). The final fake file was exactly as expected.

**Tests.** `tests/todo.test.js` (module: parse, read, add/done/undone/reword/move/remove, every refusal, undo cases, hand edit between
calls, CRLF; brain: read as data, update, a failed update, refused after a course file, the brief names the tools) and the new rows in
`tests/refusal-rules.test.js`.

**The move (done last).** The old "## To do" section of `PROGRESS.md` became `data/todo.md` (content and order kept; a bold line
became a `##` section, each bullet or numbered entry an item; entries marked DONE/MERGED are `[x]`). `PROGRESS.md` keeps one pointer
line. A copy of the old section is at the end of this note.

**What Omri must do:** nothing, except the manager restarting Bot after the merge (the tools load at start). Claude Code sessions
read `data/todo.md` by its absolute path (CLAUDE.md).
