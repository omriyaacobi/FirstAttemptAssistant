### New finding: the slow cases are front-desk *answers* that are long

All four bad runs above (both errors, and the 69 s / 78 s medium runs) were messages where the front desk **wrote the reply itself** ("difference between a stack and a queue", "what happens when two keys collide"). Writing a paragraph inside the forced-JSON reply is slow and fails often (4 of 42 calls). The briefing said the front desk could answer "short explanations".

Fix, tested live: `router-brief.md` now says the reply must fit in one or two short sentences, and longer explanations go to `gemini-flash`. Re-test with medium:

| Message | before | after |
|---|---|---|
| "Explain in one paragraph what a mutex is" | front desk 90 s (hit the new timeout) | delegate gemini-flash, 10.4 s |

(The destination model's own time, about 6 s for Flash, comes on top, so these still come out far under 70 s.) Edit the line in `router-brief.md` if you disagree.

## 4. Research: can Bot be cheaper or faster?

**Keeping `agy` warm: yes, it works, with a catch.** `agy` has `--input-format stream-json` + `--output-format stream-json` ([docs](https://antigravity.google/docs/cli/headless)): the process stays open, you write one JSON line per prompt (`{"event":"user","message":{"content":"..."}}`) and read a `result` event per turn. Two quirks I hit: the first prompt must go on stdin (not `-p`), and the flag must be written `-p=` (with an empty value). Measured with Flash medium:

| | time |
|---|---|
| plain `agy -p "Reply with just OK"`, three runs | 5.7 / 6.6 / 5.7 s each |
| one warm process: `init` event | 3.3 s after start |
| turn 1 result | 6.1 s |
| turn 2 result | +2.9 s |
| turn 3 result | +2.3 s |

So a warm process answers in about **2-3 s instead of about 6 s**, saving about 3-4 s per `agy` call. **The catch:** all turns share one conversation (turn 3 remembered turns 1 and 2). For the front desk, that means old messages (maybe from other chats) leak into later decisions and the context grows, so it needs a reset or a restart every N messages. It is also a long-lived process to manage (crashes, one per model). I did **not** build this; it is a bigger, riskier change. There is also an `agy acp` subcommand (Agent Client Protocol server over stdio) and community bridges around it; I found no official documentation for it, and did not test it.

**Streaming output: yes.** `--output-format stream-json` emits `init`, `step_update` (state ACTIVE/DONE, including `agent_response`) and `result` events as the run progresses. A page could show text as it arrives, but that needs changes in `server.js` (protected), so it is a job for Claude Code.

**`--print-timeout`** exists in `agy` (default 0 = no limit). Bot's own timeout now does this job for every model and also kills the process tree.

**Gemini API key: not measured** (no key in `.env`, and I did not ask for one). It would remove the ~5-6 s CLI start (`agy` ~5.7 s for a one-word reply). Published numbers ([Artificial Analysis](https://artificialanalysis.ai/de/models/gemini-3-5-flash/providers)) show first-token time of about 1 s with minimal thinking but about 17 s with medium thinking on a 10k-token prompt, so the thinking setting matters more than the transport. It would also be a separate quota/billing from the Pro plan.

**`claude -p` startup with `--tools ""` in an empty folder: not measurable** while logged out. Verified from `claude --help` that `--tools ""` ("Use \"\" to disable all tools") and `--no-session-persistence` exist, and that the command line with `""` works through `cmd.exe` (the failure is the auth error, not a flag error). `--bare` (skip hooks, CLAUDE.md, keychain reads) looks tempting but only authenticates with `ANTHROPIC_API_KEY`, never the Pro login, so it is not usable for Bot. To measure properly once login works: run `claude -p --model haiku --tools "" --no-session-persistence` ×3 in `%TEMP%\bot-empty`.

## 5. What was built (branch `claude/speed-1e2cc8`, not pushed, not merged)

| Change | Where | Effect |
|---|---|---|
| Quota lookup off the critical path | `quota.js` | Last known value returned at once, refreshed in the background; failed refresh keeps the old value; the very first lookup waits at most 5 s (`FIRST_WAIT_MS`). Saves ~3.6 s on the first message after each 5 min. |
| Every model call in the empty folder; Claude with `--tools ""` and `--no-session-persistence` | `providers.js` | Less context to load, safer; `askAgy` was running in Bot's project folder. |
| Per-model timeouts | `providers.js` | Flash 90 s, Sonnet 3 min, Argon 4 min, Opus 5 min, other 3 min (named constants). On timeout the whole process tree is killed (`taskkill /T` on Windows; plain `kill` would leave `claude` running behind `cmd.exe`). Tested with a real stuck process. |
| Timing | `providers.js`, `core.js`, `planner.js` | See section 3. |
| Front desk on Flash medium | `frontdesk.js` | ~5 s per message. |
| Tighter front desk answer rule | `router-brief.md` | Removes the 70-90 s / failing cases. |

Tests: 235 pass (222 before; +13: 3 quota, 6 providers, 4 core).

End-to-end check with the real `handleTask` (no Claude): simple question 11.0 s (first call, quota waited 3.8 s) and 14.4 s (quota cached, front desk slower that run; variance). Before: ~3.6 s quota + 11-15 s front desk = 15-19 s for the same kind of question. The 90 s front-desk stall in the third question is what the briefing change removes, and the new timeout caps it.
