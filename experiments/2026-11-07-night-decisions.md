# Night build of the thread core: decisions made while Omri slept (2026-11-07)

Omri could not answer, so each unclear point below was settled with the safest option that keeps moving. Read this list first; change any of them by telling me.

1. **Where the course rules live in the briefings.** Both `router-brief.md` and `router-brief-haiku.md` now hold the course text between `<!--thread-->` and `<!--/thread-->` lines. Code (`briefText` in `frontdesk.js`) removes the whole block when the thread is off, so the prompt is word for word what it was before. Haiku reads its briefing as a FILE, so the right version is written to a temp file (`bot-brief-haiku-plain.md` or `-course.md`). A test fails if a block is left open or the "off" text still mentions courses.
2. **Old constants did not change.** `ACTIONS`, `SCHEMA`, `COMPACT_SCHEMA` and `REPLY_FORMAT` are exactly what they were. The thread uses new twins (`SCHEMA_COURSE`, `COMPACT_SCHEMA_COURSE`, `REPLY_FORMAT_COURSE`). Reason: the old tests and the "off means identical" rule.
3. **A `course` decision with an empty course** ("what should I study today?") is allowed by the check, and core.js answers with a code-written question "Which course is this about? Your courses: ...". No model is called. The study tracker (another chat) will replace this with a real plan.
4. **A course named but not in the real list = invalid decision** (the desk retries, then Haiku decides). A name that fits exactly one course loosely ("Calculus" for "Calculus 2") is accepted; one that fits two ("Programming") is refused.
5. **Photos in the thread** still skip the front desk and go to Gemini like today (a photo cannot become a course question yet). They take a slow slot.
6. **Where the slow-lane slot is taken.** The front desk reads every message with no limit. The slot is taken by `gate()` (a function `jobs.js` gives to `core.js`) just before slow work: a model answer, the planner, a course answer, a photo. The speculative Flash answer that starts alongside the desk is not counted (it is Gemini, and plentiful).
7. **Same-course order is best effort.** A message waits for an earlier one only after the desk has decided both are for the same course. Two messages sent in the same second may both reach the notebook; the second then just does not see the first answer.
8. **Question topic.** A user message is written the moment it is sent, before the desk decides, and a line is never edited, so its `topic` stays `general`. The answer carries the real topic (`course:<id>`, `calendar`, `study`, `general`); the pair's topic is the answer's. Recall and the labels read it from the answer.
9. **Labels in the history** (`Assistant [course answer: Calculus 2]`) are written by code from `result.mode === "course"`; imported course answers get the name through `courseName(id)`.
10. **Push text.** In the thread the lock screen shows "An answer about your studies/your calendar/your message is ready" and never the message or the answer.
11. **Empty answer = failure** in thread jobs only (the old `start()` stays exactly as it was). `askChain` already treated an empty model answer as a failure and moves to the next model.
12. **Context size.** Recent turns 6,000 characters (each message cut to 1,500 here, 3,000 in core), up to 5 "still working on" lines, and the newest calendar card note always (found within the last 400 messages, not older than 14 days; cards live 15 minutes anyway). `MAX_CONTEXT_CHARS` is the hard cap and a test builds a thread of 1,200 messages of 5,000 characters to prove it. The whole desk prompt stays under 40,000 characters in that test.
13. **Trash.** Deleting writes a tombstone line and a copy in `data/thread/trash/`; nothing is rewritten. Only Bot's own 6-hourly timer (`purgeTrash`) removes a message after 30 days, by rewriting that one day file. A model has no way to call trash, restore or purge. The page routes are `DELETE /api/thread/<id>` and `POST /api/thread/<id>/restore`.
14. **Import ids.** An imported message gets `m_` + 16 hex characters from a hash of (old chat id, place in the chat). So the same message always has the same id; the second run adds nothing. A chat that grew gets only its new messages. A message trashed in the thread is not brought back by a re-import.
15. **Import never writes outside `data/thread/`.** The CLI defaults to the real `data/`; tests and my check used a temporary copy (`--data <folder>`). Export refuses any folder inside `data/conversations` and any non-empty folder.
16. **Recall.** `findInThread` pairs by `replyTo`, includes course turns (the one-conversation rule), skips calendar replies and morning briefs as before, and also searches old chats that were never copied into the thread (not twice). The reply text "Chats inside a course ... are not searched" in `core.js` is now only half true with the thread on; left alone for the page chat to reword.
17. **Course deletion.** `DELETE /api/courses/<id>` still deletes that course's OLD chat files (unchanged code). Thread messages are never touched by it, and imported copies of those chats stay in the thread.
18. **Old routes with the switch off.** `/api/conversations`, `/api/ask` with a chat id, the 409 "one task at a time per chat" and course chats all work as before; tests prove it. With the switch on, `/api/ask` ignores `conversationId` and `courseId`.
19. **Study state and the tracker.** `createJobs` takes `studyState()` (one line per course, written by code) and passes it to the front desk under "## Courses". It returns "" until the tracker chat plugs in.
20. **Not done on purpose:** the page (`public/index.html`), the daily summary, the tracker and tutor, the morning brief appending to the thread. Other chats do them.
